What I learned

Where are the data, control and management planes in your network?

The management plane is represented by topology.yaml and the Python scripts. build_topo.py checks the description and creates the Mininet network, while make_page.py generates its documentation. My network has 3 switches, 6 hosts and 8 links, with host addresses in 10.16.0.0/24 and fd00:2616::/64.

There is no central SDN controller because the network uses LinuxBridge switches with controller=None. The switches use their existing MAC-learning behaviour, while the hosts use ARP and IPv6 Neighbour Discovery to learn address mappings. These are the local control functions in this network.

The data plane sends and forwards packets using the information in these tables. The Linux bridges use their MAC tables to choose output ports, and hosts use their neighbour tables to send packets to the correct MAC addresses. My evidence/macs.txt and evidence/neigh.txt show these tables.

How did your switches learn which port leads to each host? Use your MAC table evidence.

The switches learned by recording the source MAC address and incoming port of Ethernet frames. When a frame arrived, the switch learned that its source MAC address could be reached through that port.

In evidence/macs.txt, switch s1 learned h1's MAC address, 00:00:00:00:00:01, on port 1 and h2's MAC address, 00:00:00:00:00:02, on port 2. These hosts are directly connected to s1.

The MAC addresses of h3, h4, h5 and h6 were all learned on port 3. This matches my topology because port 3 connects s1 to s2, and all four hosts are reached through that link. A single switch port can therefore lead to several hosts through other switches.

Which of the four kinds of programmability is this assignment (a network described as data, then built and documented by scripts)? Why isn't it any of the other three?

This assignment demonstrates automated configuration management, category (d). I describe the intended network in topology.yaml, then use Python scripts to validate the description, create the Mininet network and generate documentation. The programmable part is the workflow that turns configuration data into a running network and its documentation.

It is not programmable data plane, category (a), because I do not change how packets are parsed, matched or processed using tools such as P4 or BMv2. The Linux bridges keep their existing packet-forwarding behaviour.

It is not external control plane, category (b), because I do not use an SDN controller to make forwarding decisions through OpenFlow. My network uses LinuxBridge switches with controller=None and their existing MAC-learning behaviour.

It is not programmatic device interfaces, category (c), because I do not use structured device-management interfaces such as NETCONF, RESTCONF or gNMI, or a YANG data model, to read and write device configuration. Instead, my scripts read a local topology file and use Mininet's Python API to create the lab network.

Week 1's 2 a.m. change on 40 switches: what would be different if those switches were described like your network?

The engineer could edit a shared network description instead of entering commands separately on 40 switches. This would make the intended change easier to review and reduce repeated manual work.

Validation could catch some mistakes before deployment. For example, evidence/check.txt shows my script detecting duplicate IPv4 and IPv6 addresses and a link to the unknown node s9. These checks would not catch every possible problem, but they would identify these errors before building the network.

With suitable deployment automation, the validated description could be applied consistently across the 40 switches. In this lab, build_topo.py creates a Mininet network rather than updating real switches, and make_page.py separately generates documentation from the same description. Changes would still need testing after deployment.

What's the difference between your network's data model and its serialisation? Use YAML and JSON as the example.

The data model defines the structure and meaning of the network information. In my project, it includes student_id_last4, a list of switches, hosts with names and IP addresses, and links joining pairs of nodes.

Serialisation is the text format used to store that information. YAML uses indentation and list markers, while JSON uses braces, brackets and quoted keys. Both formats can represent the same network data model.

The load() function reads either format into a Python dictionary containing lists and other values. The resulting dictionaries are equal only if the two files contain equivalent data. Converting between YAML and JSON changes the representation, so the topology information must be kept consistent in both files.

Why is it better to catch bad data in check() than with pingall? What did IPv6 notice about a duplicate address that IPv4 didn't?

check() can identify configuration errors before the network is built. In evidence/check.txt, it reports that h1 and h2 share 10.16.0.1 and fd00:2616::1, and that a link refers to the unknown node s9. These messages point directly to errors in the description.

pingall tests reachability after the network is running. A failed ping shows a connectivity problem, but it does not by itself explain whether the cause is an address conflict, an incorrect link or another issue. Validation and connectivity testing are therefore both useful.

In evidence/dad.txt, IPv6 Duplicate Address Detection marked the duplicate fd00:2616::1/64 address on h2 as "dadfailed tentative", preventing its normal use. In the same experiment, the manual IPv4 address-add command accepted 10.16.0.1/24 as a secondary address without rejecting the duplicate. This describes the behaviour observed in my experiment; it does not mean IPv4 can never detect address conflicts.

What does your Git history give you that copying files into folders named topology-v2-final wouldn't?

Git records committed versions of my files, including the changes, author, time and commit message. I can compare versions to see exactly how the topology, scripts and documentation changed. Meaningful commit messages also explain why I made each change.

Git lets me restore a known working version of the topology and scripts together. This is easier to track than several folders with names such as topology-v2-final. However, I still need to run each script with the correct file path; Git does not choose the input file automatically.

Keeping the source data, scripts, evidence and generated page in one repository also makes the work easier to review. After changing the source files, I can regenerate the HTML, commit the updated files and publish the generated page through GitHub Pages.
